# v0.2 R4.2 — Isolated generation worker: operator runbook

The worker VM runs untrusted generated code (Astro builds, and generated
JavaScript in Chromium) inside per-job bubblewrap sandboxes. Railway stays
the trusted control plane. **The worker holds no platform secret**; it has
only its claim-only worker token.

Nothing here is automatic. Every step that buys, provisions or changes
production needs the owner's explicit authorization, and **no secret value
is ever pasted into chat, a doc, a commit or shell history**.

## 0. Pilot host

| | |
|---|---|
| Recommended | Hetzner Cloud **CX33**: 4 vCPU (shared), 8 GB RAM, 80 GB NVMe, KVM |
| Location | Nuremberg or Falkenstein (DE), or Helsinki (FI) |
| OS | **Debian 13** (unprivileged user namespaces on by default; no AppArmor userns restriction) |
| Access | the owner's SSH key added at creation; no password login |
| IPv4 | keep a public IPv4 unless Railway's API origin is confirmed reachable over IPv6 (verify cost) |
| Backups | not required. The VM holds no state that can't be reinstalled; jobs are in Railway Postgres. |
| Minimum viable | 2 vCPU / 4 GB / 40 GB. Lower `SandboxLimits.memory_bytes` to ≤ 2.5 GB and expect slower Visual QA. |

Verify the current price on the provider's page at purchase time.

## 1. Provision the host (owner)

1. Create the VM (above) with your SSH key. Note its IP.
2. `ssh root@<vm-ip>`, then `apt-get update && apt-get -y upgrade && reboot`.

## 2. Install the worker (root on the VM)

```bash
git clone --depth 1 https://github.com/<owner>/generate-web-ai.git /root/gwa-src
/root/gwa-src/deploy/worker/install.sh https://github.com/<owner>/generate-web-ai.git <release-commit-or-tag>
```

This installs:
- packages: bubblewrap, Node 24, uv, Chromium and its dependencies, nftables and unattended-upgrades;
- the unprivileged `gwa-worker` user, with lingering enabled so its user manager can create per-job cgroup scopes;
- the release at `/opt/gwa-worker/releases/<commit>`, with the `/opt/gwa-worker/current` symlink pointing at it;
- the systemd units and drop-ins;
- the firewall (`/etc/nftables.conf`);
- key-only SSH, applied **only** if an authorized key is present;
- journald size caps.

It does **not** start the worker.

For a private repository, clone with a read-only deploy key installed only
for root, and use the SSH repo URL. Never put a token in the URL.

## 3. Install the worker credential (root on the VM)

The token is generated **on the VM** and never displayed. Only its SHA-256
leaves the VM; the hash is not usable as a credential.

```bash
install -d -m 0755 /etc/gwa-worker
( umask 077; openssl rand -hex 32 | tr -d '\n' > /etc/gwa-worker/worker-token )
chown root:root /etc/gwa-worker/worker-token && chmod 0600 /etc/gwa-worker/worker-token
tr -d '\n' < /etc/gwa-worker/worker-token | sha256sum | cut -d' ' -f1   # -> GENERATION_WORKER_TOKEN_SHA256
```

Set `GWA_API_BASE_URL=https://<railway-api-public-domain>` in
`/etc/gwa-worker/worker.env`. That file holds no secrets.

## 4. Host probes (quick sanity check, as the worker user)

```bash
sudo -u gwa-worker unshare --user --map-root-user true && echo userns_ok
sudo -u gwa-worker unshare --user --map-root-user --net --pid --fork true && echo net_pid_ok
test -f /sys/fs/cgroup/cgroup.controllers && echo cgroup_v2
```

These probes are indicative only. **The acceptance suite is authoritative.**

## 5. R4 host acceptance (authoritative)

It runs in the exact hardened service environment of the worker:

```bash
systemctl start gwa-worker-acceptance.service
journalctl -u gwa-worker-acceptance.service -o cat --no-pager | tail -40
```

**Required:** `R4_HOST_ACCEPTANCE=PASS`, every `PROBE`/`DIMENSION` line `PASS`,
and `suite` with 0 failures, errors and skips.

Record the full output in the R4.2 evidence section of
`docs/v0.2-generative-website-architecture.md`.

**If it fails, STOP.** Do not configure Railway or start the worker. Report
the failing lines.

On Ubuntu instead of Debian, AppArmor blocks unprivileged user namespaces
for unconfined programs. Add an AppArmor profile for `/usr/bin/bwrap`
granting `userns`, and re-run acceptance. Never set
`kernel.apparmor_restrict_unprivileged_userns=0` host-wide.

## 6. Configure Railway (owner, only after PASS and explicit authorization)

In the Railway dashboard → service `generate-web-ai-repo` → Variables, enter
the values directly. Never paste them anywhere else.

| Variable | Value |
|---|---|
| `GENERATION_WORKER_TOKEN_SHA256` | the hash printed in step 3 |
| `GENERATION_WORKER_SIGNING_KEY` | a fresh random value you generate locally (`openssl rand -hex 32`) and paste only into Railway |
| `GENERATIVE_WEBSITE_BUILDS_ENABLED` | **leave unset / false** (the S0 gate stays OFF) |

Both worker variables unset means the worker endpoints return 404.

To verify without printing values, check that
`POST /internal/generation-worker/claim` without a token answers **401**
(configured), not 404.

## 7. Start the worker

```bash
systemctl enable --now gwa-worker.service
journalctl -u gwa-worker.service -o cat -f
```

Expect a ready self-test line, then idle claims. There are no job logs
until a job is queued.

## 8. Controlled infrastructure E2E (gate stays OFF, no provider call)

Use a dedicated test business in a test tenant; the live site is never
touched. Run it inside the API's environment on Railway:

```bash
railway ssh --service generate-web-ai-repo -- \
  python -m app.worker.fixture_job --tenant-id <tenant-uuid> --business-id <business-uuid> \
  --api-base-url https://<railway-api-public-domain>             # dry run: writes nothing
# then the same command with --confirm   ->  R4_FIXTURE_JOB_QUEUED job_id=… draft_id=…
```

Then check:
- **Worker log:** `job started` then `job finished … status=succeeded … report=accepted`.
- **Draft:** the draft is `ready`, with `artifact_sha256` set and the Visual QA findings and screenshots present.
- **Preview:** create a preview from Studio or `POST …/website-drafts/<draft-id>/preview`. It opens behind Cloudflare Access.
- **STOP before publish.** Publishing needs a separate owner authorization.
- **Live site:** the production site and its version history are unchanged.

## 9. Operate

**Update:**
```bash
install.sh <repo-url> <new-commit>
systemctl start gwa-worker-acceptance.service
```
If acceptance passes, run `systemctl restart gwa-worker`.

**Roll back the worker release:**
```bash
ln -sfn /opt/gwa-worker/releases/<previous-commit> /opt/gwa-worker/current.new
mv -T /opt/gwa-worker/current.new /opt/gwa-worker/current
systemctl restart gwa-worker
```

**Rotate the worker credential:**
1. Repeat step 3, which overwrites the token.
2. Update `GENERATION_WORKER_TOKEN_SHA256` in Railway.
3. Run `systemctl restart gwa-worker`.

The old token stops working as soon as Railway has the new hash.

**Rotate the signing key:** replace `GENERATION_WORKER_SIGNING_KEY` in
Railway. Jobs in flight fail and are never READY: their results are
refused, and their leases expire as `worker_lost`.

**Logs:** `journalctl -u gwa-worker`. They contain the worker id, job id,
attempt, status, safe failure category and durations. They never contain
tokens, source, BusinessTruth or the environment.

## 10. Kill switches (any one stops external generation)

1. **S0 gate** (`GENERATIVE_WEBSITE_BUILDS_ENABLED`): stays **false**. It is
   the global kill switch for the generative product path.
2. **Worker service:** `systemctl stop gwa-worker` (and `systemctl disable`
   it). A running job's sandbox dies with the worker; its job fails as
   `worker_lost` at the next claim, and the draft goes `BUILD_FAILED`, never
   READY.
3. **Credential:** unset `GENERATION_WORKER_TOKEN_SHA256` (or both worker
   variables) in Railway. The claim endpoint then answers 404 and the worker
   backs off harmlessly. Rotating the token revokes it.

**Emergency:** do (2) and (3). Nothing on the worker can publish or deploy,
so the live sites are unaffected either way.
