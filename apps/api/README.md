# @generate-web-ai/api

The backend control plane's domain model: Tenant, User, Business, Website,
Workflow, WorkflowVersion, Integration, Credential, Execution, Template.
Python + FastAPI-stack (SQLAlchemy, Alembic, Pydantic), per the target
architecture's decision to keep the AI orchestration and automation
control plane on Python/FastAPI/Pydantic while the client-facing sites
stay on Astro (`packages/renderer`, unrelated to this app).

```
Business                  <- the central entity
  -> website:      Website | None       (1:1, unique on business_id)
  -> workflows:     Workflow[]          (each with versions: WorkflowVersion[])
  -> integrations:  Integration[]       (each with credential: Credential | None)
  -> executions:    Execution[]         (a Workflow run or a Website build)
```

Every business entity carries a denormalized `tenant_id` back to `Tenant`
(not just via its parent) — deliberate defense-in-depth for tenant
isolation, enforced again at the data-access layer by
`TenantScopedRepository` (`app/repositories/base.py`), which every
repository except `TenantRepository` extends.

## Layout

- `app/domain/enums.py` — the vocabulary (`BusinessVertical`,
  `WorkflowStatus`, ...) shared by the DB models and the Pydantic
  schemas, defined once so the two layers can't drift apart.
- `app/db/models/` — SQLAlchemy 2.0 declarative models. `str_enum()`
  (`columns.py`) is required for every enum column — SQLAlchemy's
  `Enum` type persists the Python member's `.name` by default, not its
  `.value`, which would silently desync from the CHECK constraints,
  Pydantic schemas, and any future JSON API that all speak in `.value`.
- `app/schemas/` — Pydantic `*Create`/`*Read` pairs. `extra="forbid"`
  everywhere; cross-field rules live here too (e.g. a `WorkflowVersion`
  can't be `approved`/`published` without `approved_by_id` +
  `approved_at` — Section 5's human-confirmation requirement; an
  `Execution`'s `workflow_id`/`website_id` must match its `type`).
- `app/repositories/` — thin, tenant-scoped data access. Extra query
  methods only where they add real value (`get_by_email`,
  `next_version_number`), not one-per-entity boilerplate.
- `app/services/credential_service.py` — the only place plaintext
  secrets and the Fernet key meet (`app/security/encryption.py`).
  `CredentialRead` has no secret/encrypted-value field at all, so a
  future endpoint can't leak one by naively serializing the ORM object.
- `migrations/` — Alembic, autogenerated from `Base.metadata`.
- `app/main.py` — FastAPI app factory: CORS (Studio's dev origin only),
  structured exception handlers (`app/errors.py`), the `GET /health`
  router. `app/dependencies.py` holds the process-lifetime engine/session
  factory FastAPI dependency-injects per request.
- `app/errors.py` — every error path (an `AppError` a route raises on
  purpose, a Pydantic validation failure, a routine HTTP error, an
  unhandled bug) renders the same `{"error": {"code", "message",
  "details"?}}` shape. Unhandled exceptions are logged with a traceback
  server-side but never leak their message to the client.
- `app/domain/business_config/` — `BusinessConfig`: the structured
  source of truth for a business (business_profile, brand, website,
  lead_management, communications, integrations, automation). Pure
  Pydantic domain data — no FastAPI/SQLAlchemy/n8n/AI-SDK imports.
  Mirrors `packages/site-config`'s shapes where they overlap
  (brand/theme colors, SEO, postal address) rather than redefining them
  incompatibly; deliberately does **not** mirror `SiteConfig`'s
  page/block content tree (that stays business-INTENT-level — see
  `website.py`'s docstring). `examples.py` has a complete, realistic
  fixture (`EXAMPLE_REFORMA_VALENCIA_CONFIG`).
- `app/routers/businesses.py` + `app/services/business_service.py` —
  `POST/GET/PUT/DELETE /businesses(/{id})`. `Business.config` (JSON) /
  `config_schema_version` hold the serialized `BusinessConfig`;
  `Business.name`/`vertical`/`slug` stay as relational columns too
  (a deliberate, documented projection for cheap listing/uniqueness —
  see the `Business` model's docstring) — the two aren't auto-synced yet.
  Tenant scoping comes from `get_current_tenant_id`
  (`app/dependencies.py`), an `X-Tenant-Id` header — **not real
  authentication**; see that function's docstring before exposing this
  to anything but a trusted internal caller.
- `app/analysis/` — the AI Business Analyzer: `BusinessAnalyzer` (ABC) +
  `BusinessAnalysisResult`/`BusinessAnalysisOutput` are provider-neutral;
  `app/analysis/claude/` is the first implementation, over Claude's
  Messages API structured-output path (`client.messages.parse`, no
  tools/function-calling surface at all). `app/analysis/assembly.py`
  turns the LLM's raw output into an actual, schema-validated
  `BusinessConfig` — never inventing a fact, always falling back to
  `missing_information`/`questions` instead of a guess. Exposed as
  `POST /businesses/analyze` (`app/routers/businesses.py`), which never
  persists its result — a human reviews the proposal before any
  `POST/PUT /businesses` call saves it. Requires `ANTHROPIC_API_KEY`
  (`app/config.py`); returns 503 if unset.

## What's deliberately not here yet

No real integration (OAuth) flows, no billing, no `WorkflowConfig`
(executable) — out of scope so far
(see the architecture's AI boundary). `Website.config` /
`WorkflowVersion.definition` are still opaque JSON; deep validation
against the real generated-website/workflow shapes arrives with the
AI-generation phase. No authentication — see `get_current_tenant_id`
above.

## Running it

```sh
uv sync                      # installs deps + creates .venv
uv run pytest -q             # 104 tests: schema validation, tenant isolation,
                              # DB constraints, serialization, encryption,
                              # health endpoint, error handling, BusinessConfig
                              # schema/persistence/API-isolation
uv run ruff check .          # lint
uv run mypy app               # typecheck
uv run alembic upgrade head  # applies migrations (DATABASE_URL env var,
                              # defaults to a local sqlite file)
uv run uvicorn app.main:app --reload   # dev server, GET /health at :8000
```

Or via Docker Compose from the repo root (`docker compose up --build`) —
brings up Postgres, this service, and `apps/studio` together. See the
root `docker-compose.yml`.

**Website publishing (`app.publishing.build`) does not work inside that
Docker image yet.** It shells out to a real `astro build` in the sibling
`apps/site-builder` app, which needs Node + pnpm and the rest of the
monorepo checkout on disk — the Dockerfile here is a plain
`uv`/Python image built from `apps/api` alone, with neither. Until the
image is updated to include them, run this service natively (`uv run
uvicorn app.main:app --reload`, from a full monorepo checkout with `pnpm
install` already run) to exercise `POST /businesses/{id}/website/publish`
for real. Every other endpoint is unaffected.
